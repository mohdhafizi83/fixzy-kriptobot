Fixzy Kriptobot Daemon — Operation Blueprint

Step-by-step walkthrough of bin/bot_daemon.php execution logic

Updated 2026-05-21 · Based on source code audit (6 rounds, 0 bugs remaining)

1. Daemon Lifecycle Overview

The daemon is invoked by cronjob every minute. It holds a file lock to prevent overlapping runs and executes for a maximum of 55 seconds, processing "ticks" every 10 seconds.

  1. Lock acquired — bot_daemon.lock via flock(LOCK_EX|LOCK_NB)
  2. Database connection — Doctrine DBAL singleton
  3. Service init — BotRepository, TradeLogger, ExecutionGuard, NotificationService
  4. Centralized Data Hub — Batch-fetch all market prices into APCu shared memory (15s TTL)
  5. Daily Maintenance — If all bots IDLE and cache expired, refresh available pairs list
  6. Recovery Map — Build per-user recovery bot index
  7. Bot Loop — Iterate all enabled bots, process each through Situasi D → C → A → B
  8. Early Exit — If no active deals exist, stop ticks and end script
  9. Lock released

2. Centralized Data Hub (Batch Fetch)

To avoid API rate limits when running hundreds of bots, the daemon fetches all market tickers in one API call at the start of each tick cycle and caches them in APCu shared memory with a 15-second TTL.

if (function_exists('apcu_store')) {
    // 1. Get distinct exchange names from user_api_keys
    // 2. For each exchange, check if cache is fresh (apcu_fetch hub_status key)
    // 3. If stale: fetch all tickers in ONE call → store each price in APCu
    //    Key format: kriptobot_price_{exchange}_{symbol}  (e.g. kriptobot_price_binance_BTC/USDT)
    // 4. Individual price reads then hit RAM in <1ms (zero API call)
}
Cache key consistency: Exchange name is always strtolower()'d both when writing (Data Hub) and reading (ExchangeService::getCurrentPrice), ensuring cache hits.

3. Bot Processing Loop (Per-Bot Flow)

For each enabled bot (bots.status = 1), the daemon reads configuration (JSON from settings.php) and runtime_state (JSON that evolves during trading). It then resolves API keys, fetches candle data for all required timeframes, and runs the evaluation chain:

Start
↓
Situasi D: Trailing Buy Tracker
↓ (if not handled)
Situasi C: Limit Order Tracker
↓ (if not handled)
Situasi A: Active Deal (has holdings)
↓ (if no holdings)
Situasi B: IDLE (hunt for entry)

Bot state is persisted to DB via repo->updateRuntimeState() at key checkpoints and at the end of each bot iteration. On the next tick, the state is decoded from the DB and processing resumes where it left off.

4. Situasi D — Trailing Buy Tracker

WAITING_TRAILING_BUY — Bot is waiting for price to bottom out and bounce before buying.

Trigger: $state['status'] === 'WAITING_TRAILING_BUY' && !empty($state['trailing_symbol'])

  1. Fetch current price of trailing_symbol from exchange
  2. Call TrailingEngine::evaluateTrailingBuy(price, lowWatermark, deviation%)
  3. If WAIT: Update low water­mark (tracking new lows), save state, continue
  4. If TRIGGERED: Bounce detected! Set $readyToBuySymbol, clear trailing state, fall through to Situasi B for execution

Enables buying at the absolute bottom after a price reversal, rather than on the initial dip.

5. Situasi C — Limit Order Tracker

WAITING_LIMIT — Bot has placed a limit buy order on the exchange and is waiting for it to fill.

Trigger: $state['status'] === 'WAITING_LIMIT' && !empty($state['limit_order_id'])

Order StatusAction
closed Set state to ACTIVE with average_entry_price from fill. Flow to Situasi A.
canceled / expired Reset to IDLE. If clone bot → delete. If parent → save state.
open (pending) Fallback to Market: Cancel limit order → execute market buy for remaining USDT → set ACTIVE

"Try Limit 1st" strategy: attempts limit order to save fees, falls back to market buy within 10 seconds if not filled.

6. Situasi A — Active Deal (Has Holdings)

ACTIVE — Bot currently holds coins. Full risk-management evaluation chain runs.

Trigger: $state['current_holdings'] > 0 && $state['average_entry_price'] > 0

Evaluation Order (A1 → A3):

A1. Global Sell Override (Master Exit)

If global filters are enabled and global sell conditions pass (Logical AND via BaseOrderConditionEngine), execute immediate market sell of all holdings. Bot resets to IDLE. State is only reset on successful sell (guarded by try-catch).

A1.5. Custom Sell Conditions (Logical OR)

Iterates risk_management.sell_conditions + global sell conditions. If any condition passes (RSI, Bollinger, TradingView Webhook, External Signal, AI Sentiment):

  • Check Minimum Profit Guard — if enabled and trade hasn't reached min profit % or timeout, sell is blocked
  • If guard passes → market sell all holdings → reset to IDLE

A2. Take Profit & Partial Sell

Calculates dynamic target profit based on TP type:

  • average_price: Target = target_profit% above current average entry
  • base_order (3Commas logic): Dynamic target scaled down as DCA increases total position: dynamicTarget = targetProfit × (baseOrderUsdt / totalUsdtVolume)

Partial Sell (if enabled):

  • Split holdings into fractions at each target % milestone
  • Sell one fraction per tick, marking targets as executed
  • When all targets sold → bot resets to IDLE

Full Take Profit (if partial sell not enabled and PNL ≥ dynamic target):

  • Check Trailing TP: If enabled, tracks price upwards and sells only on drop-back by trailing_tp_deviation%
  • Execute market sell of all holdings
  • If clone bot → delete from DB
  • If parent bot with recovery active → disable bot (graceful shutdown)
  • If recovery bot → update recovered_so_far, check if deficit cleared → restore all bots & self-delete

A2.5. Cut Loss & Trailing Stop Loss

Hard Cut Loss: If PNL ≤ –cut_loss_percent% → immediate market sell.

Trailing Stop Loss: Tracks highest price (trailing_sl_watermark). If price drops cut_loss_percent% below the tracked high → sell.

Smart Recovery Initiation (if enabled):

  • Calculate lostUsdt (absolute USD loss) and remainingUsdt (remaining value)
  • If existing recovery bot exists → merge deficit and capital into it
  • If no recovery bot → disable all IDLE bots, create new RECOVERY BOT with conservative strategy:
    • RSI < 30 + Bollinger Lower for entry
    • 5 DCA steps, 2% drops, 1.5× volume scale
    • Fixed 1% target profit, no trailing, no cut loss

A2.7. Limit DCA Tracker

If dca_limit_order_id exists, fetch order status from exchange:

  • Filled → Update holdings & average entry, increment DCA step, clear ID, notify
  • Canceled/Expired → Remove ID, allow re-placement
  • Pending → Skip further DCA checks this tick

A3. DCA (Safety Orders)

If DCA steps remain and no limit order is pending:

Limit DCA (placed_on_exchange = yes):

  • Calculate cumulative drop % using geometric series: sum(baseDrop × stepScale^i)
  • Target price = base_order_price × (1 − cumulativeDrop%)
  • DCA amount = baseOrderAmount × volumeScale^(step+1)
  • Place limit buy order, store ID in state

Market DCA (live tracking):

  • Check global DCA filters (Logical AND)
  • Evaluate DcaConditionEngine:
    • Price drop check — current price must be at least price_drop_trigger% below average entry (cumulative per step)
    • If custom_conditions_enabled: evaluate custom DCA conditions (RSI, Bollinger, QFL, Webhook, AI)
    • If trailing_enabled: wait for price bounce (TrailingEngine) before buying
  • Execute market buy for calculated amount, update average entry and holdings
  • All state updates and trade logs are only performed if newHoldings > 0 (guarded against zero-fill edge case)

7. Situasi B — IDLE (Hunt for Entry)

IDLE / WAITING_TRAILING_BUY (post-trigger) — Bot has no holdings and is scanning for a new entry.

Step 1: Recovery Quarantine

If user has an active recovery bot and this bot is NOT the recovery bot, gracefully shut down (set status = 0). This prevents idle bots from opening new positions while recovery is active.

Step 2: Market Scanner

Based on general.pair_strategy:

StrategyBehavior
singleUse the single pair from coin_pair
custom_listIterate pairs from custom_pairs (TomSelect field)
top_10_volumeMarketScannerService fetches top 10 by 24h volume
top_10_volatilityMarketScannerService fetches top 10 by volatility
top_50_globalTop 50 global market cap coins

Step 3: Per-Coin Evaluation

For each candidate coin (up to 5, break on first buy):

  1. Fetch price + candles (if TA conditions exist) — lazy-loaded per coin
  2. Run AI Cross-Verification (if news_sentiment condition exists and the AI API key is configured) — cached for 5 minutes per coin
  3. Check Global Base Buy Filter (Logical AND) — must pass all global conditions
  4. Evaluate BaseOrderConditionEngine (Logical AND) — all bot conditions must pass (RSI, Bollinger, QFL, Webhook, External Signal, AI, Start ASAP)
  5. Check ExecutionGuard — cooldown period, max deals limit, blacklist
  6. Trailing Buy check:
    • If enabled → set state to WAITING_TRAILING_BUY, start tracking. Composite bot (max_active_deals > 1) clones itself.
    • If disabled → set $readyToBuySymbol, break to execution

8. Execution Block (Base Order Buy)

Runs when $readyToBuySymbol !== null (set by Situasi D or situasi B non-trailing path).

Phase 1: Capital Allocation

  • AUTO: True Free Balance = Wallet Balance − Reserved DCA Funds for active bots. 90% of this is split equally among IDLE AUTO bots.
  • If bot already has active children (Composite), uses previously locked capital.
  • Custom: Uses the fixed amount set in settings.

Phase 2: Intelligent Capital Split

Divides capital by number of concurrent deals (max_active_deals), capped by unique pairs count for custom_list. Single pair → divisor = 1.

Phase 3: Geometric Series Base Order

Ensures no DCA starvation: baseOrder = totalDealBudget / sum(volumeScale^0 + volumeScale^1 + ... + volumeScale^N)

Example: $100 budget, 3 DCA steps, 1.5× scale → Base Order = $12.30, DCA1 = $18.45, DCA2 = $27.67, DCA3 = $41.51

Phase 4: Order Execution

  • Market: Instant buy at current price
  • Limit: Place limit order, set state to WAITING_LIMIT

Phase 5: Composite Bot Cloning

If max_active_deals > 1 and buy was NOT from trailing path → INSERT clone bot into DB. Parent resets to IDLE to hunt next coin.
